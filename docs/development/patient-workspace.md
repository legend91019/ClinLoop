# 模拟患者工作台

这一版本加入患者列表、病历/查房文书和医生主动创建的跟进任务。所有资料均为虚构，数据保存在后端数据库，刷新页面后仍保留。

## 本地初始化

在同一仓库和虚拟环境下运行：

```powershell
$env:DATABASE_URL = "sqlite+pysqlite:///clinloop-local.sqlite3"
uv run python -m scripts.init_product_demo
```

命令准备旧版 `P-1001` 回归病例和 6 位模拟工作台患者（`P-2001` 至 `P-2006`），保留现有数据。再次运行不会覆盖用户修改的草稿或重复创建示例任务；预留 ID 与其他档案冲突时明确失败。已使用 Alembic 管理的数据库应先运行 `uv run python -m alembic upgrade head`，新增迁移为 `0003`。

重新启动 API 与 Worker，启动前端后打开 `http://127.0.0.1:5173/`，从患者列表选择 `P-2001`。API 端口按本机配置设置，前端 `VITE_API_BASE_URL` 必须与之对应。三个终端必须指向同一个数据库。

## 操作流程

患者工作台采用独立功能页，侧栏仅保留“患者列表”和“患者概览”。默认打开患者概览，从基本信息下方的功能卡片进入 Agent 助手、病历与查房、跟进任务、时间线、未闭环任务、流程缺口、运行轨迹和交班；子页面顶部可点击“返回患者概览”。页面和 URL 一起切换，不使用长页锚点。例如：

患者概览首先展示姓名、性别、民族、年龄、婚姻状况、出生地、职业和入院时间，不显示患者 ID 搜索框和编号横幅。患者切换通过患者列表完成。新建患者可填写上述基本资料和入院时间；入院时间以带时区的值入库，概览按北京时间显示。未填写入院时间时使用建档时间。模拟病例的新增人口资料在再次初始化时补齐缺失字段，保留已有资料和文书。

- `/?patient=P-2001&view=overview`：当前患者概览。
- `/?patient=P-2001&view=records`：病历与查房。
- `/?patient=P-2001&view=patient-agent`：患者 Agent 助手。
- `/?patient=P-2001&view=handoff`：交班草稿。

可选 `encounter` 参数用于固定就诊。浏览器前进、后退和刷新会恢复对应患者与功能页。切页保留当前患者的编辑器、任务表单和医生身份；未保存文书在本次打开的工作区内保留，刷新或切换到其他患者时仍需确认。任务查看轨迹、已提交病历创建任务、任务打开关联文书都有对应页面跳转。

1. 在上方填写医生 ID（例如 `DR-001`），角色选择“医生”。这是现有的演示身份机制。
2. 在患者列表点击一位患者。列表支持按姓名、ID、病区或床号搜索；也可新建模拟患者或再次导入示例。
3. 在“病历与查房记录”中打开已有草稿，或点击“入院病历”“查房记录”“病程记录”。模板仅提供段落结构，正文由医生填写。
4. 点击“保存草稿”保存可继续修改的版本。点击“提交记录”核对确认后锁定原文，写入患者时间线、证据和事件 Outbox；补充内容应另写病程记录。
5. 在“这位患者的 Agent 助手”查看候选任务、原文和依据，确认后创建或填写理由驳回。需要自行安排时，仍可在“患者跟进任务”填写具体事项、负责人、优先级和可选截止时间。
6. 点击“开始跟进”“标记完成”或“取消任务”，填写处理说明。已完成任务可切换到“全部任务”查看，处理记录保留。
7. 在原有“交接草稿”中生成交班。当前就诊已提交文书作为医生确认的来源记录，尚未完成的高/紧急优先级任务进入待办。

未保存的文书在切换患者/打开其他文书时提示确认。多窗口编辑使用文书版本与任务状态检查，冲突返回 409，避免覆盖别人已提交的记录。手动任务与原有自动检验随访任务共用 Open Loop 和状态转换策略；手动任务在新区域管理，原有检验演示折叠在“高级演示”中。

## 能力边界

提交记录会由真实后台 Worker 调用已配置的 provider，生成待医生审核的候选任务；确认前不创建任务。当前本地是明确标记的确定性 mock：仅从明确的后续安排提取受支持的检验随访或资料补充待办，不能代表通用语言理解。真实 DeepSeek/AgentArts 使用现有 provider 配置，未配置密钥时不调用付费服务。每份文书最多分析当前步数预算内的分句，超限或模型失败会保守退出并显示原因。

首次查房按入院时间加48小时计算；Worker 持续扫描未出院的模拟就诊，逾期未找到医生署名的查房记录时，创建唯一的高优先级待办。提醒展示在概览、病历与查房、跟进任务内，浏览器关闭时仍会入库；没有短信或微信推送。新建患者的责任医生取创建者，旧模拟患者尚未分配时标为“主管医生（待分配）”。签署查房记录后提醒自动关闭；逾期完成会保留标记。缺少入院时间时不猜测截止时间。模板不生成诊断或治疗建议。已有身份头仍不是生产认证，未接入真实医院系统。

## 问诊与查房转录、起草和签署

在“病历与查房”中选择生成记录类型，再点击“开始语音转录”。使用浏览器 SpeechRecognition/webkitSpeechRecognition，语言为 zh-CN，显示临时识别并追加确定文字；离开查房页、隐藏浏览器页签或卸载工作区时停止麦克风。识别服务、中文支持与网络由浏览器决定，不保证每种浏览器可用；失败时保留确定文字并允许输入或粘贴。系统仅保存文字，不保存音频。本次会话未保存文字暂存在当前浏览器 sessionStorage，按患者与就诊隔离。

点击“保存对话并生成病历”后，原文以不可修改的 INTERVIEW 来源记录保存，Worker 消费独立的 INTERVIEW_SAVED 事件并生成 DRAFT 病历。重复请求不会重复生成，失败可从原文历史重试。患者可以先开始录入，保存时才要求填写医生身份，避免原先新增按钮被无说明禁用。

默认“正式病历草稿（真实模型）”调用独立的临床文书撰写器，将原始对话、患者资料、本次就诊检查和既往已提交文书综合改写为连贯的临床叙述，支持入院病历、查房记录和病程记录三种结构。原始对话和检验 JSON 不直接拼入正文。初稿的每条叙述保留来源标识，待补充信息与冲突单独列出供医生核对。没有医生明确评估或安排时，不自行补诊断、体征、用药或治疗计划。

病历撰写与任务分析使用独立配置：即使 AGENT_PROVIDER=mock，正式文书仍调用 NOTE_DRAFT_PROVIDER=deepseek。请在仓库根目录 .env 中配置 DEEPSEEK_API_KEY，保留现有 DEEPSEEK_BASE_URL、DEEPSEEK_MODEL 或按账号实际可用型号修改。NOTE_DRAFT_PROVIDER 默认 deepseek。配置完成后重启 API 与 Worker。/clinical-writing/config 只返回提供方、型号及是否配置，不返回密钥。未配置时会保存原文并明确标为生成失败，不伪装成模型成功，也不会自动退回模板。

“文书格式演示（本地模板）”仅用于无模型时预览结构与少量口语改写，标题及页面均明确标注未调用模型，不能作为真实生成质量的证明。已有对话可以按当前选择的方式重新撰写，创建独立新文书，不覆盖旧草稿或已签署记录；重复请求不会重复生成版本。旧对话整理草稿仍可查看。

撰写器通过 get_labs 读取同次就诊、生成请求前最近30天内最多20份检查结果，并读取请求前最近10份已提交文书；保留来源及时间，旧记录不直接当作本次事实。数值、来源标识、章节结构及仅引用提问等错误有自动校验；语义支持、医学表述和遗漏仍由医生审核。原始资料过大或模型失败时明确报告，不静默截断。

医生可以对照原文修改草稿，填写签名并勾选审核确认后提交。签署记录保存署名、医生身份、时间及版本，签署后锁定；签署前不建立医生确认的证据、不创建任务。签署后复用原来的文书 Agent，仅从新格式正文的“诊疗计划”中提取候选任务，检查总结、诊疗评估及待补充提示不作为新的医嘱。医生确认候选后进入结果等待、检验事件唤醒、证据核验、医生确认并闭环的既有流程。

## 患者 Agent 完整体验

1. 选择任意模拟患者并填写医生身份，点击“试写 Agent 查房示例”，得到“血培养结果出来后提醒我查看；补充患者过敏史”。可以编辑后再提交。
2. 提交后自动排队，Worker 使用只读工具读取当前就诊记录和检验，按分句调用 provider，核对患者与证据引用，生成候选。页面每两秒更新一次。
3. 在助手区域核对原文、任务目标和依据，点击“确认并创建任务”；不需要的建议填写原因后驳回。反复确认同一候选不会重复创建任务，同项目已在等待时会拒绝重复创建，避免匹配歧义。
4. 结果随访任务挂起等待。在助手中展开“模拟当前患者的检验结果到达”，选择血培养/药敏/血常规/肾功能并发送合成报告。重试同一请求不会重复写入。
5. 原有 WorkflowAgent 自动匹配患者、就诊和项目，调用 get_labs/get_progress_notes，保存证据与待审核提示，任务进入结果待查看。其他患者或项目的结果不会推进任务。
6. 核对原始结果后点击“查看后确认并闭环”，或“确认并继续跟进药敏”，填写医生处理说明。此操作也确认本任务的未响应提示；Worker 再次核验引用后完成状态转换，必要时建立药敏依赖任务。
7. 查看分析轨迹或任务跟进轨迹，了解 provider、工具调用和停止原因。交班继续复用原有高优先级未闭环任务与证据。

已有提交记录可点击“让 Agent 分析这份记录”。失败后支持重试；Worker 未运行时页面会显示排队提醒。血培养到达后才人工确认结果，系统不会替医生确认检验或直接出具诊疗意见。

## 关键接口

- `GET/POST /api/v1/patients`：患者目录与新建模拟档案。
- `POST /api/v1/demo/patients`：幂等导入六位示例患者。
- `GET/POST /api/v1/patients/{id}/documents?encounter_id=...`：文书列表/新建草稿（创建时就诊 ID 在请求体）。
- `PATCH /api/v1/patients/{id}/documents/{document_id}`：携带 revision 修改草稿。
- `POST /api/v1/patients/{id}/documents/{document_id}/submit`：核对版本后提交。
- `GET/POST /api/v1/patients/{id}/tasks`：查询/创建手动跟进任务。
- `GET /api/v1/patients/{id}/first-round?encounter_id=...`：首次查房截止、签署及逾期完成状态。
- `GET/POST /api/v1/patients/{id}/interviews`：查询/保存问诊原文；POST 携带 encounter_id、request_id、transcript、kind。
- `POST /api/v1/patients/{id}/interviews/{interview_id}/retry`：起草失败后重新排队，保留原文。
- `GET /api/v1/clinical-writing/config`：查询模型配置状态，不包含密钥。
- `POST /api/v1/patients/{id}/interviews/{interview_id}/draft`：携带 request_id、draft_mode（CLINICAL/DEMO），从同一份原文撰写新版本。
- `PATCH /api/v1/patients/{id}/tasks/{loop_id}`：携带 expected_state 和 reason 更新任务。
- `GET /api/v1/patients/{id}/agent-workspace?encounter_id=...`：候选、分析状态和 Agent 任务。
- `POST /api/v1/patients/{id}/documents/{document_id}/analyze`：旧记录分析或失败重试。
- `POST /api/v1/patients/{id}/documents/{document_id}/candidates/{candidate_id}/review`：审核候选任务。
- `POST /api/v1/patients/{id}/agent-labs`：当前就诊的合成检验结果事件。
- `POST /api/v1/patients/{id}/agent-tasks/{loop_id}/acknowledge`：医生确认结果，并可建立药敏依赖。

所有写接口要求显式的医生身份头，接口校验患者与就诊、来源文书归属。文书新表同时提供 SQLite/PostgreSQL 的 Alembic 迁移。
